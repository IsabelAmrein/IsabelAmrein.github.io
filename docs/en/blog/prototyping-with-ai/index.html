Prototyping with AI: from idea to something you can test

prototypinggenerative-aivibe-codingproduct

If an AI can write an application in minutes, what becomes valuable is knowing how to ask for it and how to check it. That was the idea of the last class of the week, on prototyping applications with AI, taught by Ander Toledo.

The technique is called vibe coding: describing an idea, generating a first version, testing it and iterating on the result. The term was born in 2025, when agents went from helping to write code to building and testing applications.

According to the 2025 DORA report, cited in class, 90% of respondents use AI at work and 30% say they have little or no trust in the code it generates. The figures describe that sample. It is used a lot and trusted little, which is why knowing how to verify the output matters.

The class worked on it with one practical case, an interactive sales viewer, and with the document used to commission something more serious: the PRD. What mattered was not the tool, but how it was requested and how it was checked.

The process changes: from implementing to describing, observing and adjusting

With AI, the work moves from translating decisions into code to describing, observing and adjusting. The classic process of building software has four steps: need, design, implementation, and validation and use. The new process proposed in class also has four: describe what the user needs and what data we have; build a first version with a small scope; observe it by using it with a known case; and adjust, by asking for a change and checking again.

What is new is not the steps but the loop: adjusting forces you to check again.

That splits the work differently:

Read a project’s contextWhich problem deserves solving

The right-hand column answers the question the class started with: what still depends on us.

A request you can check

The difference between a good and a bad result starts with the request. “Make me a nice dashboard with this CSV” cannot be checked: it does not say who uses it, which question it answers or when it is right.

The class proposed a concrete brief, with context, defined metrics and filters, the expected result and its limits, and leaving the visual look until after you have settled what the tool must do.

For something more serious, a PRD

A viewer hides decisions that a short brief does not make: which metric to show, with what scale, what to do with missing data and how to interpret it. To make those decisions in writing, the class used a PRD.

A PRD, or product requirements document, defines what to build, for whom and how to evaluate the result. It is handed to the AI together with the request, and it has four parts:

  • Problem and user: which need we solve and for whom.
  • Scope: what the product includes and what stays out.
  • Requirements: the functions, data and rules it must meet.
  • Acceptance criteria: how we will check that it works.

Acceptance criteria are written as situations with their expected result: for example, if a filter leaves no records, the viewer shows “no data”.

What I take away

Prototyping with AI does not remove the work of judgement: it brings it forward. The class summed it up in four lessons:

  • The prototype reveals questions. Seeing it, missing requirements appear.
  • Design can be too convincing. A polished interface can also calculate wrongly.
  • Autonomy needs context. The tool fills in whatever we do not specify.
  • Domain knowledge brings judgement. We know which result makes sense and why.

And four habits to start with:

  1. A concrete problem: one person, one need and one decision.
  2. Enough context: data, units, constraints and an example.
  3. A small version: the minimum flow that lets you learn.
  4. Visible acceptance: known results before building.

Changes, besides, must be small and recoverable: one intention per change, the working version saved before moving on and a check afterwards.

A version-controlled repository, such as GitHub or Azure Repos, makes that natural: each small change is a commit with a message stating its intention (“sort products by revenue”), new work is tested on a branch without touching the working version, and if something goes wrong you go back in one step.
